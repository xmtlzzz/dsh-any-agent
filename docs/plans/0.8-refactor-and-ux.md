> 关联文档：[架构说明](../zh/architecture.md) · [权限与隐私](../zh/security.md) · [使用注意事项](../zh/caveats.md) · [测试体系](../zh/tests.md)

## 1. 范围与非目标

本文聚焦 `v0.7.9` 之后迈向 `0.8` / `1.0` 最具投入产出比的两块工程改进：

- **目标 A（核心可维护性）**：把体量过大的 4 个核心模块拆清边界，保持零依赖、零循环引用、对外导入路径零破坏，并在不引入 `devDependencies` 的前提下补强跨模块类型与结构护栏。
- **目标 B（开箱体验与认知负担收口）**：把三处需要用户反复翻文档才能避开的体验断点，尽量变成默认安全或运行期自解释——① 常驻模式（`DSH_MCP_DAEMON=1`）的平滑默认化与防卡死降级；② DSH GUI 写锁冲突与工作区登记覆盖的主动护栏；③ 面向调用方与 CLI 的双语错误文案彻底收口。

**明确非目标**：

- **不覆盖 macOS / Linux 真机实测扩展**：非 Windows 平台继续沿用现有 CI 模拟 ACP 套件即可，不做额外真机矩阵投入。
- **不试图解耦 DSH 内部格式**：本服务的定位就是给 DSH 派活，读取 `app.asar`、`session_projcache`、`workspace.json` 与 `dsh-acp` 协议属于产品定位内的合理耦合，继续跟随 DSH 版本演进与 `dsh_doctor` 兜底即可。
- **不破坏既有对外契约**：MCP 工具面、哨兵 `schema: 1`、live 事件流 `v: 1` 及客户端配置格式一律保持向后兼容（由 [test/contract.mjs](../../test/contract.mjs) 守住）。

## 2. 核心模块拆分方案

### 2.1 现状盘点（`v0.7.9` 实测）

`src/` 下目前有 51 个 `.mjs` 文件，整体模块化已经较好，但头部 4 个文件集中了过高的复杂度：

| 文件 | 行数 | 当前痛点 | 拆分优先级 |
|---|---:|---|---|
| [src/conversation.mjs](../../src/conversation.mjs) | 1,684 | 单个 `Conversation` 类承载了进程生命周期、写锁抢占、审批桥接、审核落盘和单回合执行；仅 `prompt()` 就占 327 行（L835–1161）。 | **P1（核心）** |
| [src/clients.mjs](../../src/clients.mjs) | 1,234 | 将文件原子备份、JSONC 字符区间扫描器、TOML 行级编辑器、10 个客户端定义、安装/修复/卸载编排全部混在一个文件里。 | **P0（最先拆，纯函数占比最高）** |
| [src/hub.mjs](../../src/hub.mjs) | 935 | 混杂注册表持久化、14 个 `runStore` 薄透传、磁盘会话兜底采纳、`session/list` 探测缓存、空闲/RSS 回收器与优雅关机。 | **P2** |
| [src/tools.mjs](../../src/tools.mjs) | 885 | 15 个 MCP 工具处理器全部内联在 `createHandlers()` 的一个 820 行闭包对象字面量里。 | **P2** |
| [src/live-view.mjs](../../src/live-view.mjs) / [src/workspace.mjs](../../src/workspace.mjs) | 870 / 836 | 内部已按逻辑分段、耦合度低、变更频率也较低。 | **暂缓观察** |

### 2.2 拆分硬约束

1. **严格零依赖**：[test/package-check.mjs](../../test/package-check.mjs) 守住零 `dependencies`，[scripts/lint.mjs](../../scripts/lint.mjs) 也约定不引入 `devDependencies`。
2. **目录结构天然兼容构建与检查**：`package.json` 的 `"files"` 已包含 `"src/"`（递归打包），[scripts/lint.mjs](../../scripts/lint.mjs) 的 `collectFiles()` 也已递归遍历 `src/**`，不需要改任何打包或 lint 入口。
3. **外观门面零破坏**：现有测试和入口直接从 `src/hub.mjs`、`src/clients.mjs`、`src/tools.mjs`、`src/conversation.mjs` 导入具名符号（例如 `test/failure-terminal.mjs` 从 `hub.mjs` 导 `Conversation`，`test/config-safety.mjs` 从 `clients.mjs` 导 `scanJson` / `editJsonEntry` / `editTomlBlock`）。拆出的子目录文件均由原入口文件做薄 `export { ... } from ...` 门面，保证既有 41 套离线测试零修改通过。
4. **单向无环**：子模块严禁反向 import 门面文件或上层编排器（例如 `conversation/*` 绝不 import `hub.mjs`）。

### 2.3 `src/clients.mjs` → `src/clients/`（P0，最先落地）

该文件注释里已经自然划出了 5 块边界，直接按边界拆目录即可，零业务风险：

```text
src/
├─ clients.mjs              # ~35 行：纯门面 re-export，保持 bin/setup.mjs、bin/restore.mjs 与全部测试路径不变
└─ clients/
   ├─ io.mjs                # ~120 行：backupSuffix/backupFile/pruneBackups/atomicWrite/isWritable/readConfigFile/sourceHashOf/backupTexts/settleRemoval
   ├─ jsonc.mjs             # ~370 行：scanJson/detectEol/detectIndentUnit/renderValue/editJsonEntry/stripWs/jsonProperty/sameJsonArgs/repairJsonLaunch
   ├─ toml.mjs              # ~260 行：multilineMask/tomlKeys/findTomlRanges/trimRanges/inlineTomlFields/assertTomlEnvString/copyTomlEnv/editTomlBlock/repairTomlLaunch
   ├─ registry.mjs          # ~170 行：ENTRY_NAME/entryShape/describeEntry/resolveDirs/existingShapeMode/clientList/isPresent/defaultLaunch/codexBlock/desiredEnv/managedEnvKey
   └─ plan.mjs              # ~150 行：planClient/applyClient
```

**依赖方向**：`io.mjs`、`jsonc.mjs`、`toml.mjs` 互不依赖 → `registry.mjs` 依赖 `io` + `jsonc` → `plan.mjs` 依赖全部四者 → `clients.mjs` 仅做导出汇总。

**收益**：新增 MCP 客户端只需改 `registry.mjs`；修 JSONC/TOML 边界 bug 不再干扰客户端策略逻辑；单测可以直接针对语法器做更轻量的用例。

### 2.4 `src/conversation.mjs` → `src/conversation/`（P1，核心瘦身）

沿用 0.7.8 拆出 `src/conversation-live.mjs` 和 `src/run-ledger.mjs` 的成功经验：**保留 `Conversation` 作为单一状态持有者与外部入口，把 4 块重逻辑抽成纯函数/协作器模块**（避免过度拆类导致状态分散和循环引用）：

```text
src/
├─ conversation.mjs              # ~460 行：Conversation 构造、状态快照(toState/toMeta/snapshot)、onUpdate、输出/队列薄委托、方法入口
└─ conversation/
   ├─ turn.mjs                   # ~380 行：原 prompt()(327 行) + #startWatchdog(50 行) + #settleFailedRun(40 行) + formatReasoning
   ├─ lifecycle.mjs              # ~320 行：ensureAlive(129 行) + verifyPermissionRecorded(55 行) + takeover(92 行) + close(102 行)
   ├─ approval.mjs               # ~160 行：onPermissionRequest(77 行) + decideApproval(23 行) + 审批挂起/取消辅助
   └─ review-flow.mjs            # ~130 行：pendingReviewTicket + submitReview(107 行)
```

**`turn.mjs` 内部二次拆解（解决 327 行巨型 `prompt()`）**：

把单回合流水线拆成 4 个平铺阶段函数，每段控制在 60–90 行以内：

1. `prepareTurn(conv, text, opts)`：检查 forget/busy、创建 `RunRecord`、写 `.running` 接单标记、发 `live.startTurn()`、采回合前 Git 快照。
2. `runAcpTurn(conv, run, collector, opts)`：启动看门狗（`startWatchdog`）、调用 `session/prompt`、处理超时降级后台与 `AbortSignal`。
3. `finalizeTurn(conv, run, collector, acpRes)`：先 `checkpointRunResult` 落盘防崩溃丢正文 → 采终态 Git 快照 → 挂审核单 → 原子写完成哨兵 → `live.endRun()`。
4. `failTurn(conv, run, collector, err)`：统一收口进程退出、看门狗终止、`ensureAlive` 失败与异常终态，确保 `interject` 等待者唤醒和失败哨兵落盘不遗漏。

**依赖方向**：`conversation/*` 仅接收 `conv` 实例作为入参，只 import 底层工具模块（`locks.mjs`、`watchdog.mjs`、`review.mjs`、`git-snapshot.mjs`、`acp-session.mjs` 等），绝不 import `conversation.mjs` 或 `hub.mjs`。

## 3. 第二点（开箱体验断点与认知负担）解决方案

前文评估中指出的三处开箱体验短板，每一处都可以用相对聚焦的改动解决，且不牺牲已有安全边界。

### 3.1 常驻进程模式（`DSH_MCP_DAEMON=1`）：从隐藏开关到安全默认

#### 当前痛点

1. Windows 上 MCP 客户端用 Job Object 拉起 stdio 服务，关闭或重连客户端会连带杀掉 DSH 子进程、打断运行中回合；但默认安装（`dsh-any-agent-setup --yes`）仍关闭常驻模式。
2. [bin/setup.mjs](../../bin/setup.mjs#L115-L116) 当前语义是“不带 `--daemon` 重跑 setup 会把已开启的 `DSH_MCP_DAEMON=1` 静默去掉”，与 0.7.9 新增的“重跑 setup 保留自定义环境变量”预期不一致。
3. [src/daemon.mjs](../../src/daemon.mjs#L170) 的 `runProxy` 启动超时默认 `15_000ms`；万一某台机器因安全软件拦截 named pipe 导致常驻进程起不来，等满 15 秒再退回普通模式，容易逼近客户端的 `startup_timeout_sec = 20.0` 握手上限。

#### 解决方案

1. **调整 `dsh-any-agent-setup` 的默认与保留策略**：
   - **默认开启常驻模式**（`dsh-any-agent-setup --yes` 写入 `DSH_MCP_DAEMON=1`），同时新增 **`--no-daemon`** 显式退回直连 stdio 模式。
   - **重跑不静默翻转**：用户未显式传 `--daemon` 或 `--no-daemon` 时，若客户端配置中已存在 `DSH_MCP_DAEMON`，按既有值保留（仅在 `--reset-env` 或显式传 `--daemon` / `--no-daemon` 时改写）。
   - **预览输出透明告知**：在 `setup` 汇总里明示 `daemon : on (idle exit 10m; pass --no-daemon for direct stdio)`，让用户知道背后有一个空闲 10 分钟自动退出的常驻进程。
2. **缩短 `runProxy` 降级等待预算**：
   - 将 `runProxy` 的 `startTimeoutMs` 默认值从 `15_000ms` 降至 **`6_000ms`**，前 1 秒以 80ms 间隔探测（正常本地拉起通常 < 600ms，减少首连延迟），之后按 200ms 轮询；超时后仍留有 14 秒余量无缝退回普通 stdio 模式，不会触发客户端启动超时。
   - 若降级发生，在内存里记一条一次性诊断原因（如 `daemon_fallback_reason`），供 `dsh_doctor` 暴露。
3. **在 `dsh_doctor` 中增加 `daemon` 检查项**：
   - 明确展示当前运行模式（`daemon` vs `direct`）、endpoint id、常驻进程 PID、空闲回收时间；若本次是以“常驻启动失败降级为直连”运行的，报告 `warn` 并给出日志路径（`daemon-<id>.log`）。
4. **增加轻量运维子命令（可选，0.8.x）**：
   - `dsh-any-agent daemon status`：读取 `<状态目录>/daemon-*.json` 列出当前存活的常驻进程（PID、版本、启动时间）。
   - `dsh-any-agent daemon stop`：安全通知本机残留的常驻进程优雅退出（无须用户手动去任务管理器找 Node 进程）。

### 3.2 DSH GUI 写锁冲突与工作区覆盖：运行期主动护栏

#### 当前痛点

1. **GUI 永久抢锁**：空闲 10 分钟回收进程释放写锁后，只要用户在 DSH GUI 点开过该会话，`dsh web` 会在整个进程生命周期内永久占锁（切走会话、归档均不释放）。调用方只看到锁冲突报错，不知道“为什么切走了还不行”。
2. **工作区登记被 GUI 内存覆盖**：本服务写入 `~/.dsh/storages/workspace.json` 后，若运行中的 DSH GUI 做了工作区操作，会用内存旧状态覆盖磁盘，导致 MCP 会话突然掉回“未分组”。

#### 解决方案

1. **把“原因 + 三步恢复”直接写进写锁冲突报错（`src/locks.mjs` `describeLeaseConflict()`）**：
   - 当 `lock_holder === 'none'`（外部持有，99% 为 DSH GUI）时，错误正文直接给出可执行的准确说明，不再依赖用户去翻 `caveats.md`：
     - 明确告知：该会话可能已在 DSH GUI 打开，且 **`dsh web` 切走会话也不会释放写锁**；
     - 恢复方式：**重启 DSH 桌面端 / `dsh web`** 即可归还写锁，历史与产物无损；
     - 预防方式：查看运行进度请使用 **`dsh-any-agent watch`** 或 **`dsh-any-agent dashboard --open`**（只读旁路，永不碰写锁）。
2. **在 `dsh_start` 首次返回中补一句极简防踩坑提示**：
   - 仅在 `dsh_start` 的人类/模型回执末尾附一行轻量提示（不影响结构化字段）：查看实时进度请用 `dsh-any-agent watch` / `dashboard --open`，避免在 DSH GUI 点开运行中会话。
3. **给“防抢锁”提供有界内存的推荐档位**：
   - 现状 `DSH_MCP_IDLE_TTL_MS` 默认 10 分钟、且文档只提了“设 `0` 永不回收”。实际上 `DSH_MCP_MAX_LIVE=4` 已经把活跃进程数封顶了。
   - 在 `dsh_doctor` 与 `setup` 提示中，推荐需要频繁打开 GUI 旁观的用户延长空闲回收（如 `DSH_MCP_IDLE_TTL_MS=1800000` 或 `0` 配合 `DSH_MCP_MAX_LIVE=4`），让 MCP 在工作期间握住写锁，此时在 DSH GUI 点开会自动降级为**只读查看**，两边互不干扰。
4. **`dsh_doctor` 新增 `workspace_sync` 漂移检测**：
   - 当 `REGISTER_WORKSPACE !== 'off'` 时，抽查本服务注册表中最近活跃的项目会话是否仍在 `~/.dsh/storages/workspace.json` 的 `sessionIds` 里。
   - 若发现已登记的项目会话从 `workspace.json` 消失（典型特征：被运行中 DSH GUI 内存写回覆盖），报告 `warn`，提示先退出/重启 DSH 后运行 `dsh-any-agent-workspaces --backfill`。
