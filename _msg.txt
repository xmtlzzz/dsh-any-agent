refactor: make the backups recoverable, not just present

Setup has always written <file>.bak-dsh-<stamp> before touching a config,
in both directions: registering backs up so a bad install can be undone,
removing backs up so a bad removal can be reinstalled. In practice that was
one third of the job. The rest was missing:

  - You were not told where the backup went. --json had no field for it and
    the human output never printed it, so "there is a backup" was true and
    useless. Each client row now carries `backup`, and the human output
    prints `backup: <path>` under every written entry.
  - Two runs inside the same millisecond produced the same filename and the
    second copy silently replaced the first. The replaced copy could be the
    only state worth returning to. A colliding name now gets -2, -3, ...
  - Finding the right copy meant browsing five directories and guessing.
    bin/restore.mjs handles it: --list (newest first), --latest,
    --stamp, --file, --dry-run, --json. A restore is also destructive, so it
    copies the current file aside as .bak-dsh-pre-restore-<stamp> first -
    a mistaken restore can itself be undone.

This is what makes the earlier guarantee usable rather than nominal: the
claim was "we only touch our own entry and we keep a copy", but a copy you
cannot locate or restore is not a way back.

Tests: config-safety.mjs grew from 386 to 403 checks. Section 17 asserts
that both directions leave a backup whose bytes equal the pre-operation file
and that the path is reported; section 18 damages a config on purpose and
requires restore to bring back a usable file, the pre-restore copy to hold
the broken bytes, and --list --json to parse. Offline total is 632 across
nine suites, all green; the real home stayed byte-identical (0/7) while a
preview ran against it.
